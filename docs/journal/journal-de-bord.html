Étape 1 — Squelette du dépôt

16 octobre 2026 · Exigences concernées : C2 (nombre d'agents fixé au lancement), livrable « reproductible sur une autre machine, versions figées ».

Objectif

Poser le cadre dans lequel tout le code viendra se ranger : un environnement Python isolé et reproductible, une arborescence qui suit l'architecture, des outils de qualité, et un fichier de configuration qui centralise tous les paramètres d'un run.

Ce qui a été fait

  • Environnement virtuel .venv créé à partir de Python 3.12.10. Toutes les bibliothèques du projet y sont installées, rien sur le reste de la machine.
  • Arborescence : un dossier par composant de l'architecture (sim, agents, llm, bus, rag, indicators, bridge, replay), plus corpus, godot, configs et tests. Chaque paquet Python porte une phrase qui dit à quoi il sert.
  • pyproject.toml : fiche d'identité du projet. Il déclare les dépendances directes avec leur version exacte, configure ruff (style et erreurs courantes) et pytest.
  • requirements.lock : liste complète et figée de toutes les bibliothèques installées, y compris les dépendances indirectes.
  • .gitignore : exclut l'environnement virtuel, les caches, le fichier de secrets .env, les sorties de runs et le cache de Godot.
  • .env.example : modèle du fichier de secrets, sans valeur (adresses d'Ollama, Kafka, Redis ; clés d'API facultatives).
  • Configuration : configs/default.yaml et son chargeur sim/config.py, plus la liste des 11 rôles dans agents/roles.py.
  • 11 tests automatisés dans tests/test_config.py.

Comment fonctionne la configuration

Un run est entièrement décrit par un fichier YAML en quatre sections :

SectionContenuValeur par défaut
runGraine du générateur aléatoire42
simulationDurée simulée en jours, mode d'exécution90 jours, synchrone
mondeNom de marque, ingrédient phare, indice de protection (fictifs)valeurs provisoires
populationNombre d'agents pour chacun des 11 rôles120 agents, dont 84 LLM

Au chargement, load_config vérifie chaque valeur. Sont refusés : une durée nulle, une graine négative, un mode autre que synchrone ou asynchrone, un nom de marque vide, un rôle inconnu, un effectif négatif, une population vide, et toute clé mal orthographiée (par exemple duree_jour au lieu de duree_jours). L'erreur indique le fichier et le champ fautif.

Lien avec l'exigence C2. Pour changer le nombre d'agents, on modifie la section population du fichier YAML, ou on crée un autre fichier dans configs/. Le code ne change pas. Un test le vérifie avec une population de 4 agents.

Objectif

Mettre en place les deux services qui tournent à côté de la simulation : Kafka, le bus par lequel passent tous les événements, et Redis, qui garde l'état courant du monde. Vérifier que le code Python sait y écrire et y relire.

  • sim/settings.py : lit les adresses des services dans .env. Sans fichier .env, les valeurs par défaut conviennent pour un poste local.
  • Trois bibliothèques ajoutées : aiokafka (client Kafka compatible avec asyncio, que l'orchestrateur utilisera), redis (client Redis, avec une version asyncio) et python-dotenv (lecture de .env).

Choix de configuration et leurs raisons

ChoixRaison
Kafka en mode KRaft, un seul nœudDepuis Kafka 4, ZooKeeper n'existe plus : Kafka gère lui-même ses métadonnées. Un seul nœud suffit sur un portable.
Une partition par topicKafka ne garantit l'ordre qu'à l'intérieur d'une partition. Avec une seule partition, tous les événements d'un topic sont relus exactement dans l'ordre d'écriture, ce qui est indispensable pour rejouer un run à l'identique (E3). Le débit d'une partition dépasse de loin nos quelques dizaines de milliers d'événements par run.
Rétention de 7 joursKafka sert de transport, pas d'archive. L'historique durable sera écrit en Parquet à l'étape 8 (F3).
Création automatique des topics désactivéePar défaut, Kafka crée un topic dès qu'on écrit dedans. Une faute de frappe dans un nom créerait alors un topic fantôme où les événements se perdraient sans erreur. Désactivée, l'erreur est immédiate.
Mémoire de Kafka limitée à 1 GoLaisse la RAM aux autres composants. Mesuré au repos : 360 Mo pour Kafka, 5 Mo pour Redis.
Redis sans persistance sur disqueL'état courant est reconstruit à chaque run ; le sauvegarder ne servirait à rien et ralentirait les écritures.
Ollama hors de DockerSous Windows, donner le GPU à un conteneur ajoute de la complexité sans bénéfice (décision du document d'architecture).

Étape 3 — Mesure de la machine

16 octobre 2026 · Exigences concernées : E4 (coût d'un run), E5 (sobriété), A5 (modèles de tailles différentes), et l'objectif O4 (identifier le facteur limitant).

Objectif

Remplacer les durées supposées du document d'architecture par des durées mesurées sur la machine du projet, avant d'écrire le moindre agent. On sait ainsi combien de temps durera un run, combien de mémoire graphique prend chaque modèle, et ce que coûte le passage d'un palier à l'autre.

Ce qui a été fait

  • Téléchargement des trois modèles Qwen3 : qwen3:1.7b (1,4 Go), qwen3:4b (2,5 Go), qwen3:8b (5,2 Go). Le premier réseau plafonnait à 140 Ko/s ; le changement de réseau a permis de finir à environ 10 Mo/s.
  • Réglage d'Ollama par six variables d'environnement utilisateur (tableau ci-dessous), prises en compte au redémarrage d'Ollama.
  • Script de benchmark llm/benchmark.py, relançable sur n'importe quelle machine (python -m llm.benchmark), y compris celle de la collaboratrice.
  • Résultats enregistrés dans docs/mesures/ : un résumé lisible (Markdown) et toutes les mesures brutes, appel par appel (JSON).
  • Bibliothèques ajoutées : ollama (client officiel, qui servira aussi à l'étape 6) et httpx (requêtes HTTP simples).

Comment on a mesuré

Chaque appel imite une décision d'agent : un prompt d'environ 650 tokens (profil, jour, zone, météo, trois messages reçus, quatre passages « retrouvés »), une réponse JSON imposée (action, sens, message, justification), la réflexion de Qwen3 désactivée. Les prompts varient d'un appel à l'autre, mais de façon déterministe, pour que le benchmark soit reproductible. Le nom de marque vient de la configuration, jamais du code.

Pour chaque modèle : un chargement à froid, 12 appels l'un après l'autre, puis 12 appels par paquets de 2 et de 4 en parallèle. Pendant chaque série, nvidia-smi relève quatre fois par seconde la puissance, la mémoire et la température du GPU. On mesure enfin la bascule de palier : charger le 8b alors que le 1.7b et le 4b sont en mémoire, puis revenir au 1.7b.

Ce que les mesures nous apprennent

Les latences confirment les hypothèses, et le 8b est même plus rapide que prévu (2,1 s au lieu de 3 s).Le dimensionnement tient. Pour les 2 155 appels estimés d'un run : environ 41 min en séquentiel, environ 25 min avec le meilleur parallélisme de chaque palier.
Le parallélisme double le débit du 4b et du 8b et divise par deux l'énergie par décision.Argument direct pour la sobriété (E5) : regrouper les appels coûte moins cher.
La bascule de palier est coûteuse : charger le 8b décharge à la fois le 1.7b et le 4b (6,5 s), et revenir coûte environ 3 s par modèle. Un aller-retour ≈ 13 s. Si le palier grand est appelé un jour sur deux, cela ajoute environ 10 minutes par run. L'ordonnancement par palier (étape 5) doit limiter le nombre de bascules.

Étape 5 — Horloge simulée et orchestrateur (mode synchrone)

Le déroulé d'une journée

  1. 00:00 : l'horloge publie le début du jour, puis les acteurs du monde publient leurs événements (météo…).
  2. 10:00 : chaque agent reçoit sa perception, construite sur l'état de la veille : sa zone, la météo, la part de porteurs autour de lui, les messages qui lui ont été livrés, les perturbations survenues.
  3. Seuls les agents déclenchés réfléchissent : premier jour, message reçu, ou perturbation. Les autres gardent leur décision précédente, sans aucun appel (règle 10).
  4. Les agents à règles décident d'abord, puis les agents LLM regroupés par palier, avec le nombre de requêtes simultanées fixé par la configuration.
  5. Publication, dans l'ordre des identifiants d'agents : décisions, puis déplacements et messages qui en découlent.
  6. Écriture de l'état courant dans Redis.
La barrière synchrone. Le jour d, chaque agent ne voit que l'état du jour d-1. L'ordre dans lequel les agents réfléchissent pendant la journée n'a donc aucun effet sur leurs décisions. C'est ce qui permet de regrouper librement les appels par modèle sans fausser le phénomène, et c'est ce qui distingue le mode synchrone du mode asynchrone (étape 15), où les agents rapides agiront avant les lents.

L'ordre des paliers alterne d'un jour à l'autre : petit → moyen → grand les jours impairs, grand → moyen → petit les jours pairs. Deux jours consécutifs se touchent par le même modèle, déjà chargé.

Cohérence temporelle (C6) et pannes (A4)

  • Par construction, un agent ne reçoit que les messages déjà livrés.
  • Par contrôle, si une décision cite (caused_by) une information que l'agent n'avait pas reçue, l'orchestrateur publie un incident violation_temporelle, et le compte. Un test utilise volontairement un agent « tricheur » pour le prouver.
  • Un agent qui plante ou ne répond pas produit un incident sans_reponse et garde sa décision précédente : la journée continue.
  • Une décision mal formée (message trop long…) produit un incident sortie_invalide et rien d'autre : jamais une décision publiée à moitié.

Identité et reproductibilité d'un run

  • Chaque run reçoit un identifiant lisible : 20261017-173539-default-s42 (date, configuration, graine) et un dossier runs/<run_id>/ avec un manifeste (configuration complète, graine, versions, commit git) et un bilan (compteurs).
  • Chaque agent a son propre générateur aléatoire, dérivé de la graine du run et de son identifiant : ses tirages ne dépendent pas de l'ordre de passage des autres.

Une réponse dont la forme est garantie

Le schéma JSON est donné au paramètre format d'Ollama, qui contraint la génération : le modèle ne peut écrire qu'un JSON de cette forme. Le sens et l'action ne peuvent prendre que les valeurs des catégories fermées (B1). Le schéma est propre à chaque agent : un message direct ne peut viser qu'un de ses contacts.

{ "justification": "…une ou deux phrases…",
  "sens": "efficace | tendance | banal | depasse",
  "action": "acheter | appliquer | recommander | critiquer | en_parler | ignorer | abandonner",
  "message": null
           | { "canal": "zone | reseaux", "contenu": "…" }
           | { "canal": "direct", "destinataire": "<un contact>", "contenu": "…" } }

La réponse est ensuite revalidée par Pydantic, car la contrainte d'Ollama ne couvre pas tout (texte vide, champ en trop…).

Pourquoi la justification vient en premier. Ollama écrit les champs dans l'ordre du schéma. En plaçant la justification avant le sens et l'action, le modèle formule sa raison avant de choisir, au lieu de justifier après coup un choix déjà fait.

Un essai préalable a montré que la longueur maximale imposée par le schéma coupe le texte en plein mot. Elle ne sert donc que de garde-fou (300 caractères) ; c'est le prompt qui demande des réponses courtes.

Quand le modèle échoue : relance, puis repli (A4)

  1. Réponse invalide ou délai dépassé : un incident (sortie_invalide ou sans_reponse), puis une relance, qui rappelle au modèle la raison du refus.
  2. Second échec : incident repli, et la décision vient de la règle « seuil + continuité ». Elle est publiée avec moteur = repli : on sait toujours quelles décisions ne viennent pas du modèle.

L'agent ne publie rien lui-même : il rend ses incidents avec sa décision, et l'orchestrateur les publie sur sim.incidents, rattachés à la décision par caused_by (F6). Une décision cite dans caused_by exactement les messages montrés au modèle : au plus les 8 plus récents, pour tenir dans le contexte de 2048 tokens.

Mesurer le coût (E4)

  • Chaque décision porte son coût : modèle, tokens en entrée et en sortie, durée, nombre de tentatives. Les tentatives ratées sont comptées : elles ont consommé du calcul.
  • Le bilan du run totalise appels, relances, replis, tokens et durée, par modèle.
  • Avant chaque groupe de palier, le routeur précharge le modèle : le temps de bascule est mesuré à part au lieu d'alourdir la latence du premier agent.

  • Orchestrateur : publication des incidents et bilan des coûts.

À retenir pour l'oral

  • La forme de la réponse est garantie par une contrainte de génération, puis revalidée : le sens ne peut pas sortir des quatre catégories.
  • Un modèle qui échoue ne bloque jamais le monde : une relance, puis une règle. Chaque incident est publié, compté et rattaché à sa décision.
  • Chaque décision connaît son coût, tentatives ratées comprises ; le bilan le donne par modèle.
  • Changer le modèle d'un palier est un simple paramètre : c'est ce qui rend les expériences C2 et C3 possibles.

Ce que contient l'historique

Une ligne par événement. La colonne brut garde l'événement exactement tel qu'il a circulé, et c'est elle qui sert au rejeu. Les autres colonnes reprennent l'enveloppe (type, dates simulées, jour, agent, zone, caused_by) et la position Kafka (topic, offset, horodatage, producteur, numéro de publication), pour les requêtes. En fin de run, le bilan indique combien d'événements ont été publiés et combien ont été enregistrés : les deux nombres doivent être égaux.

Le rejeu (E3)

.venv\Scripts\python -m replay.rejeu <run_id>              # tout, sans attente
.venv\Scripts\python -m replay.rejeu <run_id> --vitesse 2  # 2 jours simulés par seconde
.venv\Scripts\python -m replay.rejeu <run_id> --verifier  # bilan recalculé = bilan.json ?

Le rejeu affiche les événements avec la même fonction que la console en direct. Pour le contrôle --verifier, le bilan est recalculé avec la même classe Bilan que l'orchestrateur et dans le même ordre, si bien que même les sommes de durées tombent juste au millième près. Seuls les temps de la machine (durée totale, chargements, bascules) ne sont pas comparés : ils décrivent l'ordinateur, pas le monde simulé.

Le chemin d'une injection

  1. L'observateur envoie POST /injections. Le pont publie un controle.injection sur sim.control, daté de l'heure simulée courante du run.
  2. Avant le jour suivant, l'orchestrateur relève sim.control (un message non conforme part dans sim.dlq).
  3. À 00:00 du jour suivant, il publie une monde.perturbation dont caused_by pointe sur l'injection (F6).
  4. Les agents de la zone la perçoivent, ce qui les déclenche. Leurs décisions citent la perturbation, et leurs messages propagent l'effet.

Défauts trouvés en vérifiant

Le pont lisait l'heure du dernier état écrit. L'orchestrateur publie maintenant son heure courante au début de chaque jour : l'injection est datée juste (C3), et prend effet au jour qui suit.
  • Comptage de l'historique. L'écrivain enregistre aussi, à raison, les injections et commandes publiées par le pont pendant le run. Le contrôle de fin de run compare désormais les événements de l'orchestrateur et compte à part ceux du pont.

3. Comment un agent retrouve et se souvient

  1. Une question est formée à partir de sa situation : ses derniers messages, les événements du jour, sinon « que faut-il savoir sur cette crème ».
  2. Dans le corpus (ChromaDB, dans le processus Python) : les 4 passages les plus proches, publiés au plus tard ce jour-là et lisibles par son rôle, en privilégiant ceux qu'il n'a pas encore lus (sans cela, la fiche produit et les questions fréquentes revenaient à chaque décision).
  3. Dans ses souvenirs : les 3 plus proches, de jours passés seulement.
  4. Le tout est ajouté au prompt (« Ce que tu as lu ou entendu dire », « Ce dont tu te souviens »), et la décision publie ses sources (agent.decision en version 1.2).
  5. Après la décision, un souvenir est enregistré : ce qu'il a reçu, ce qu'il a décidé, sa raison, ce qu'il a dit.

4. Deux défauts trouvés par la mesure, et corrigés

Le sens « depasse » était compris à l'envers. Sur 23 décisions « dépassé », 17 allaient avec appliquer, recommander ou acheter : sans accent, les modèles lisaient « dépasse (mes attentes) ». Le modèle choisit désormais demode (« démodé : sa mode est passée, on n'en veut plus »), traduit en interne vers la même catégorie : le contrat d'événements, les indicateurs et Godot ne changent pas. Mesure suivante : 3 décisions « dépassé », toutes cohérentes (ignorer, en parler). Sans cette correction, l'indicateur de sens partagé (B1) aurait mesuré un contresens.
Le prompt débordait du contexte. Le plus long atteignait 2 046 tokens sur 2 048, sans place pour la réponse : Ollama tronque alors le début, c'est-à-dire la consigne de rôle. Le prompt est maintenant construit sous un budget (3,4 à 3,6 caractères par token mesurés en français ; 3,2 retenus par prudence) : on retire d'abord les messages anciens, puis le souvenir et le passage les moins proches. Les sources publiées ne citent que ce que le modèle a vu. Mesure suivante : 1 677 tokens au plus, 79 prompts réduits sur 227.

Le flacon et le commerce

Un nouveau porteur, ou un porteur dont le flacon est fini, doit acheter : là où il se trouve si c'est un point de vente fourni, sinon au mieux fourni. En rupture, sa décision est publiée mais il ne devient pas porteur, et le lendemain son prompt lui dit « tu as voulu acheter, il n'y en avait plus ». Les achats d'un même jour passent dans un ordre tiré avec la graine : par ordre alphabétique, les mêmes agents seraient toujours servis.

Deux calibrages en cours d'étape. Avec les premiers stocks, les ruptures étouffaient tout (239 achats manqués pour 112 réussis sur 60 jours). Avec un réassort fixe plus généreux, chaque flacon livré était vendu : 222 achats exactement sur 5 graines, l'offre bornait l'adoption au lieu de la dynamique sociale. Les vendeurs commandent désormais ce qu'ils ont vendu dans la semaine, avec 20 % de marge : l'offre suit la demande, et une rupture signale une demande qui s'emballe.

Un autre défaut a été corrigé : les agents de la baseline gardaient le palier de leur rôle, si bien que l'orchestrateur chargeait les modèles chaque jour pour rien. Un run C0 de 60 jours est passé de 7 min 35 s à 7 secondes.

Ce qu'est Colibrì

Un moteur d'inférence open source écrit en C (Apache 2.0), pensé pour les très grands modèles Mixture-of-Experts (MoE). Un tel modèle est découpé en centaines d'« experts », dont quelques-uns seulement servent à chaque token : Colibrì garde la partie commune en mémoire vive et lit les experts sur le SSD au moment où ils sont choisis. Il fonctionne sous Windows, avec CUDA en option, une API compatible OpenAI et jusqu'à 16 conversations en parallèle. Le projet se présente lui-même comme une plateforme de recherche.

Comment marche une journée asynchrone

  • L'heure suit le calcul. Pendant une phase, l'heure simulée avance avec le temps réel de calcul : 15 minutes simulées par seconde (simulation.asynchrone.minutes_par_seconde). Une seconde de chargement de modèle en est retirée (HorlogePhase), et l'heure ne recule jamais.
  • Chacun passe quand une place se libère. Pour chaque palier, autant d'« ouvriers » que de requêtes simultanées permises font passer les agents un par un, dans un ordre tiré avec la graine (l'ordre alphabétique favoriserait toujours les mêmes). Au passage, l'agent perçoit le monde ; s'il n'est pas déclenché, il garde sa décision.
  • Deux heures par décision (C3). sim_time_occurred est l'heure où l'agent commence à réfléchir, sim_time_processed celle où son modèle répond. Jusqu'ici, les deux étaient toujours égales.
  • La décision s'applique aussitôt. Achat (premier arrivé, premier servi), changement de porteur, messages déposés : un message de zone (sans délai) ou direct (2 h) peut être lu le jour même par quelqu'un qui passe après.
  • Pas d'information du futur (C6). La perception à l'heure s ne compte que les décisions et les messages datés de s ou avant, même si une phase les a calculés plus tard. Le contrôle des causes citées reste actif.
  • Publication en fin de journée, triée par heure simulée : la console, l'historique et Godot voient le jour dans l'ordre de ses heures.
Une information manquée, c'est un message livré à un agent avant son passage, mais calculé après lui, parce qu'il vient de la phase suivante. L'agent le lira à sa prochaine décision. C'est le prix de la contrainte de VRAM, et il est mesuré : horloge.fin_jour (version 1.1) en donne le nombre et cite les messages concernés ; le bilan le totalise et le rejeu le recalcule. En cours d'étape, un test a montré qu'une égalité à la minute près (deux agents à 08:30) comptait à tort comme un retard : la condition est désormais stricte.

L'hypothèse confrontée aux mesures

  • « Les rapides donnent le ton » : non, pour deux raisons que l'hypothèse ignorait. D'abord, le rythme réel d'un agent, c'est sa latence plus la file d'attente de son modèle : le 1.7b répond vite, mais une trentaine d'agents se partagent 2 places, si bien qu'il décide le plus tard (10:42 en médiane). Ensuite, les agents rapides ne parlent presque pas (4 messages en 60 jours) : les voix du monde sont les créateurs et journalistes (4b) et les pharmaciens (8b). Les 29 lectures du jour même vont surtout des créateurs vers les baigneurs (26).
  • « L'adoption monte plus vite au début » : oui pour la baseline, pas visible chez les agents LLM. C0 gagne 3 à 4 jours sur 5 graines. En C1, l'avance se limite à 1 ou 2 porteurs aux jours 5 et 12, puis l'asynchrone passe en dessous ; sur une seule graine, ces écarts restent dans le bruit d'un run LLM. La raison tient au délai de réflexion : un message attend le plus souvent 2 à 3 jours avant de compter (délai médian 45 h contre 48 h), quelques heures de plus ou de moins dans la journée n'y changent presque rien.
  • « Le résultat principal tient dans les deux modes » : oui pour le sens. Rôle par rôle, le sens final est le même : baigneurs « efficace » 12 sur 17 dans les deux modes, sceptiques « banal » 5 sur 8, habitués « efficace » 6 sur 8 contre 7 sur 8. L'information mutuelle finit à 0,46 contre 0,48. Pour l'adoption, il faudrait un témoin asynchrone pour le dire (étape 16).
  • Le coût caché de l'asynchrone : même nombre d'appels et même durée réelle, mais chaque appel dure 70 % de plus, parce que le 1.7b et le 4b se partagent la carte graphique au même moment. La « latence réelle » mesurée en asynchrone inclut donc cette concurrence.
  • Le prix des phases : 42 informations manquées contre 29 lectures du jour même. La séparation du 8b retarde plus de messages que l'asynchronisme n'en accélère ; 14 des 22 messages concernés viennent des pharmaciens.

Vérifications

  • 0 incident, 0 relance de modèle, 0 repli, 0 violation temporelle ; 2 961 événements publiés et enregistrés ; rejeu fidèle (bilan identique).
  • Le 42 a été compté avec la règle du run (livré au plus tard au passage) ; la règle stricte, corrigée après ce run, peut donner un peu moins si des cas étaient simultanés à la minute près.
  • 6 relances d'embedding en asynchrone, contre 0 en synchrone : 1.7b, 4b et bge-m3 travaillent en même temps, Ollama est plus chargé (constat de l'étape 17).
  • Une tranche LLM asynchrone (4 agents, 5 jours) : 12,6 s de chargement du 8b exclues de l'heure, rejeu fidèle.

Constats

  • Nouveaux : le rythme réel est fixé par la file d'attente autant que par la taille du modèle (le 1.7b décide le plus tard) ; les appels durent 70 % de plus en asynchrone (concurrence sur la carte graphique) ; plus de personnes inventées en asynchrone (32 contre 13, une seule graine) ; 42 informations manquées, surtout des messages de pharmaciens. Tous à mesurer sur 5 graines à l'étape 16.
  • Mis à jour : Ollama sous charge (6 relances d'embedding en asynchrone) ; deux tests du RAG échouent parfois dans la suite complète avec les tests Ollama, jamais seuls ni sans eux (étape 17).

Les tests

  • Horloge de phase : suit le temps réel, ignore les chargements, ne recule jamais, bornée avant le soir.
  • Lecture le jour même d'un message de zone par un agent de l'autre phase ; un message daté de la fin d'un long appel attend le lendemain.
  • Deux heures par décision et publication du jour dans l'ordre de ses heures.
  • Perception datée : un agent ne voit un porteur que si sa décision est datée d'avant son passage, même calculée plus tôt (C6) ; une cause jamais reçue est toujours détectée.
  • Informations manquées comptées, citées par la fin du jour et recalculées par le rejeu ; une égalité à la minute n'en est pas une.
  • Agents à règles à leur heure tirée, reproductible ; chargement exclu de l'heure ; parallélisme par palier respecté, une décision par agent et par jour.

Résultat : 225 tests (dont 12 nouveaux), tous réussis sans les tests Ollama (3 lancements sur 3) ; dans la suite complète, un test du RAG a échoué une fois puis réussi seul (voir les constats). Aucune remarque de ruff.

À retenir pour l'oral

  • Deux modes au choix dans la configuration. En asynchrone, l'heure simulée suit le temps de calcul, et chaque décision porte l'heure où l'agent commence à réfléchir et celle où il finit.
  • La carte graphique impose deux phases ; leur coût est mesuré (informations manquées), pas caché.
  • Q6 du jury : le résultat principal tient dans les deux modes pour le sens. La baseline montre que le modèle de temps accélère l'imitation ; chez les agents LLM, c'est le délai de réflexion qui domine.
  • L'hypothèse était fausse en partie, et c'est instructif : « rapide » ne veut pas dire « tôt » (la file d'attente compte), et ce ne sont pas les rapides qui parlent.
