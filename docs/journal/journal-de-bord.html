Étape 1 — Squelette du dépôt

16 octobre 2026 · Exigences concernées : C2 (nombre d'agents fixé au lancement), livrable « reproductible sur une autre machine, versions figées ».

Objectif

Poser le cadre dans lequel tout le code viendra se ranger : un environnement Python isolé et reproductible, une arborescence qui suit l'architecture, des outils de qualité, et un fichier de configuration qui centralise tous les paramètres d'un run.

Ce qui a été fait

  • Environnement virtuel .venv créé à partir de Python 3.12.10. Toutes les bibliothèques du projet y sont installées, rien sur le reste de la machine.
  • Arborescence : un dossier par composant de l'architecture (sim, agents, llm, bus, rag, indicators, bridge, replay), plus corpus, godot, configs et tests. Chaque paquet Python porte une phrase qui dit à quoi il sert.
  • pyproject.toml : fiche d'identité du projet. Il déclare les dépendances directes avec leur version exacte, configure ruff (style et erreurs courantes) et pytest.
  • requirements.lock : liste complète et figée de toutes les bibliothèques installées, y compris les dépendances indirectes.
  • .gitignore : exclut l'environnement virtuel, les caches, le fichier de secrets .env, les sorties de runs et le cache de Godot.
  • .env.example : modèle du fichier de secrets, sans valeur (adresses d'Ollama, Kafka, Redis ; clés d'API facultatives).
  • Configuration : configs/default.yaml et son chargeur sim/config.py, plus la liste des 11 rôles dans agents/roles.py.
  • 11 tests automatisés dans tests/test_config.py.

Décisions prises à cette étape

DécisionRaison
pip + fichier verrouOutils standards de Python, rien à apprendre en plus. Le verrou fige aussi les dépendances indirectes : la collaboratrice obtient exactement les mêmes versions.

Nom de marque provisoire MARQUE_PROVISOIRELe vrai nom sera choisi à l'étape 11 après le test de contamination. Comme il n'existe que dans la configuration, le changer ne touchera aucun code.

Comment fonctionne la configuration

Un run est entièrement décrit par un fichier YAML en quatre sections :

SectionContenuValeur par défaut
runGraine du générateur aléatoire42
simulationDurée simulée en jours, mode d'exécution90 jours, synchrone
mondeNom de marque, ingrédient phare, indice de protection (fictifs)valeurs provisoires
populationNombre d'agents pour chacun des 11 rôles120 agents, dont 84 LLM

Au chargement, load_config vérifie chaque valeur. Sont refusés : une durée nulle, une graine négative, un mode autre que synchrone ou asynchrone, un nom de marque vide, un rôle inconnu, un effectif négatif, une population vide, et toute clé mal orthographiée (par exemple duree_jour au lieu de duree_jours). L'erreur indique le fichier et le champ fautif.

Lien avec l'exigence C2. Pour changer le nombre d'agents, on modifie la section population du fichier YAML, ou on crée un autre fichier dans configs/. Le code ne change pas. Un test le vérifie avec une population de 4 agents.

Étape 2 — Infrastructure Docker : Kafka et Redis

16 octobre 2026 · Exigences concernées : C1 (événements transportés par Kafka), F3 (où vit chaque donnée), livrable reproductible.

Objectif

Mettre en place les deux services qui tournent à côté de la simulation : Kafka, le bus par lequel passent tous les événements, et Redis, qui garde l'état courant du monde. Vérifier que le code Python sait y écrire et y relire.

Rappel : à quoi servent ces deux services

ServiceRôle dans le projetPourquoi lui
KafkaJournal ordonné de tous les événements : décisions des agents, messages, météo, indicateurs, incidents. Les agents ne s'appellent jamais directement, ils publient et lisent des événements.Imposé par l'énoncé (C1). Garde l'ordre, permet de relire un flux, découple la simulation de Godot et des indicateurs.
RedisÉtat courant : stocks, météo, qui est dans quelle zone. Lu et écrit très souvent par les agents et par le pont vers Godot.Base en mémoire, réponse en moins d'une milliseconde. Les données sont éphémères (F3).

Ce qui a été fait

  • docker-compose.yml : décrit les deux conteneurs, avec des versions exactes (apache/kafka:4.3.1, redis:8.8.3-alpine) et un contrôle de santé pour chacun. docker compose up -d --wait les lance et attend qu'ils soient prêts.
  • bus/topics.py : la liste des 7 topics sous forme d'énumération Python, et la commande python -m bus.topics qui crée ceux qui manquent. Elle peut être relancée sans risque : un topic déjà présent n'est pas recréé.
  • sim/settings.py : lit les adresses des services dans .env. Sans fichier .env, les valeurs par défaut conviennent pour un poste local.
  • Trois bibliothèques ajoutées : aiokafka (client Kafka compatible avec asyncio, que l'orchestrateur utilisera), redis (client Redis, avec une version asyncio) et python-dotenv (lecture de .env).
  • 5 nouveaux tests, dont 3 tests d'intégration qui parlent aux vrais services.

Choix de configuration et leurs raisons

ChoixRaison
Kafka en mode KRaft, un seul nœudDepuis Kafka 4, ZooKeeper n'existe plus : Kafka gère lui-même ses métadonnées. Un seul nœud suffit sur un portable.
Une partition par topicKafka ne garantit l'ordre qu'à l'intérieur d'une partition. Avec une seule partition, tous les événements d'un topic sont relus exactement dans l'ordre d'écriture, ce qui est indispensable pour rejouer un run à l'identique (E3). Le débit d'une partition dépasse de loin nos quelques dizaines de milliers d'événements par run.
Rétention de 7 joursKafka sert de transport, pas d'archive. L'historique durable sera écrit en Parquet à l'étape 8 (F3).
Création automatique des topics désactivéePar défaut, Kafka crée un topic dès qu'on écrit dedans. Une faute de frappe dans un nom créerait alors un topic fantôme où les événements se perdraient sans erreur. Désactivée, l'erreur est immédiate.
Mémoire de Kafka limitée à 1 GoLaisse la RAM aux autres composants. Mesuré au repos : 360 Mo pour Kafka, 5 Mo pour Redis.
Redis sans persistance sur disqueL'état courant est reconstruit à chaque run ; le sauvegarder ne servirait à rien et ralentirait les écritures.
Ollama hors de DockerSous Windows, donner le GPU à un conteneur ajoute de la complexité sans bénéfice (décision du document d'architecture).

À retenir pour l'oral

  • Kafka est le seul moyen de communication entre composants : c'est ce qui rend un run enregistrable, rejouable et observable sans modifier la simulation.
  • Une partition par topic donne un ordre total des événements : c'est un choix délibéré au service du rejeu, pas une limite.

Étape 3 — Mesure de la machine

16 octobre 2026 · Exigences concernées : E4 (coût d'un run), E5 (sobriété), A5 (modèles de tailles différentes), et l'objectif O4 (identifier le facteur limitant).

Objectif

Remplacer les durées supposées du document d'architecture par des durées mesurées sur la machine du projet, avant d'écrire le moindre agent. On sait ainsi combien de temps durera un run, combien de mémoire graphique prend chaque modèle, et ce que coûte le passage d'un palier à l'autre.

Ce qui a été fait

  • Téléchargement des trois modèles Qwen3 : qwen3:1.7b (1,4 Go), qwen3:4b (2,5 Go), qwen3:8b (5,2 Go). Le premier réseau plafonnait à 140 Ko/s ; le changement de réseau a permis de finir à environ 10 Mo/s.
  • Réglage d'Ollama par six variables d'environnement utilisateur (tableau ci-dessous), prises en compte au redémarrage d'Ollama.
  • Script de benchmark llm/benchmark.py, relançable sur n'importe quelle machine (python -m llm.benchmark), y compris celle de la collaboratrice.
  • Résultats enregistrés dans docs/mesures/ : un résumé lisible (Markdown) et toutes les mesures brutes, appel par appel (JSON).
  • Bibliothèques ajoutées : ollama (client officiel, qui servira aussi à l'étape 6) et httpx (requêtes HTTP simples).

Comment on a mesuré

Chaque appel imite une décision d'agent : un prompt d'environ 650 tokens (profil, jour, zone, météo, trois messages reçus, quatre passages « retrouvés »), une réponse JSON imposée (action, sens, message, justification), la réflexion de Qwen3 désactivée. Les prompts varient d'un appel à l'autre, mais de façon déterministe, pour que le benchmark soit reproductible. Le nom de marque vient de la configuration, jamais du code.

Pour chaque modèle : un chargement à froid, 12 appels l'un après l'autre, puis 12 appels par paquets de 2 et de 4 en parallèle. Pendant chaque série, nvidia-smi relève quatre fois par seconde la puissance, la mémoire et la température du GPU. On mesure enfin la bascule de palier : charger le 8b alors que le 1.7b et le 4b sont en mémoire, puis revenir au 1.7b.

Ce que les mesures nous apprennent

ConstatConséquence
Les latences confirment les hypothèses, et le 8b est même plus rapide que prévu (2,1 s au lieu de 3 s).Le dimensionnement tient. Pour les 2 155 appels estimés d'un run : environ 41 min en séquentiel, environ 25 min avec le meilleur parallélisme de chaque palier.
Le parallélisme double le débit du 4b et du 8b et divise par deux l'énergie par décision.Argument direct pour la sobriété (E5) : regrouper les appels coûte moins cher.
La bascule de palier est coûteuse : charger le 8b décharge à la fois le 1.7b et le 4b (6,5 s), et revenir coûte environ 3 s par modèle. Un aller-retour ≈ 13 s. Si le palier grand est appelé un jour sur deux, cela ajoute environ 10 minutes par run. L'ordonnancement par palier (étape 5) doit limiter le nombre de bascules.
Les réponses sont plus longues que prévu : environ 110 tokens au lieu de 70.À maîtriser à l'étape 6 (justification plus courte).
Seules 2 réponses sur 117 sont invalides (1,7 %), et toutes pour la même raison : elles atteignent le plafond de 160 tokens et le JSON est coupé. Aucune réponse n'est hors schéma.Le JSON imposé fonctionne même sur le 1.7b. À l'étape 6 : plafond relevé ou réponses raccourcies, et le mécanisme « une relance puis repli » (A4) couvrira le reste.
Le 1.7b à 4 requêtes simultanées est instable : la première vague d'appels prend 4 à 12 s avant de revenir à la normale (constaté deux fois).Pour le palier petit, on visera 2 requêtes en parallèle ; 4 pour les paliers moyen et grand.
Les modèles ont une préférence : sur des situations variées, le 8b a répondu « tendance » 24 fois sur 38.Point d'attention pour la question Q2 du jury : un sens partagé peut venir du modèle lui-même et non de la diffusion. Le run témoin de l'étape 14 devra le mesurer.

Étape 4 — Contrat d'événements

16 octobre 2026 · Exigences concernées : F4 (schémas documentés et versionnés, événements non conformes isolés), C1 (granularité justifiée), C3 (deux horloges), F6 (traçabilité), B1 (sens en catégories fermées).

Objectif

Fixer, avant d'écrire le moindre agent, la forme exacte de tout ce qui circule sur Kafka. Ce « contrat » est ce que la simulation, les indicateurs, l'historique, le rejeu et Godot ont en commun : s'il est clair et vérifié, chaque composant peut être écrit et testé séparément.

Ce qui a été fait

  • bus/events.py : l'enveloppe commune et les 12 types d'événements, chacun avec son schéma Pydantic, sa version et son topic.
  • sim/domaine.py : le vocabulaire fermé du monde (7 zones, 4 sens, 7 actions) et le temps simulé.
  • bus/producer.py : publie un événement sur le topic de son type, avec accusé de réception et sans doublon.
  • bus/consumer.py : lit et valide chaque message ; un message non conforme est envoyé dans sim.dlq, compté, et la lecture continue.
  • bus/export_schemas.py : génère la documentation du contrat (docs/evenements/README.md et un JSON Schema par type) directement depuis le code. Un test échoue si la documentation n'est plus à jour.

Les deux horloges (C3). Un agent déclenché le jour 3 à 10:00 (sim_time_occurred) dont la réflexion se termine à 10:20 simulées (sim_time_processed) produit un événement émis à 14 h 32 min 05 s, heure réelle (wall_time_emitted). Le contrat interdit qu'un fait soit traité avant de s'être produit. Un message porte en plus son moment de livraison : il n'est lisible qu'à partir de cette date, ce qui servira à détecter les violations de cohérence temporelle (C6).

Les 12 types d'événements

TopicTypes
sim.world.eventshorloge.pas (début d'un jour), monde.meteo, monde.stock, monde.perturbation

Une décision indique aussi son moteur : llm, regle (agent à règles) ou repli (agent LLM retombé sur sa règle après un échec, A4). Une décision LLM porte obligatoirement le coût de son appel (modèle, tokens en entrée et en sortie, durée, nombre de tentatives) : le coût de chaque run (E4) se calculera directement à partir des événements.

Décisions prises à cette étape

DécisionRaison
Temps simulé en minutes entières depuis le jour 1 à 00:00Un pas dure un jour, mais un message peut être émis le soir et lu le lendemain midi (exemple de l'énoncé pour C3). Des entiers se comparent exactement, sans erreur d'arrondi : indispensable pour rejouer un run à l'identique et détecter une violation temporelle.
Un événement par fait observable (granularité, C1)Une décision, un message, un déplacement, un changement de météo ou de stock. Jamais un instantané complet de l'état à chaque pas : ce serait volumineux et redondant. C'est la plus petite unité qui suffit au rejeu et à la traçabilité.
7 actions fermées : acheter, appliquer, recommander, critiquer, en parler, ignorer, abandonnerComme pour le sens, une liste fermée évite le texte libre, raccourcit les réponses des petits modèles et rend les décisions comptables. On pourra l'étendre en incrémentant la version du schéma.
JSON validé par Pydantic plutôt qu'Avro avec un registre de schémasLisible à l'œil, natif en Python, sans serveur supplémentaire. Les JSON Schema exportés jouent le rôle de documentation formelle.
Documentation générée depuis le codeElle ne peut pas être fausse : un test vérifie qu'elle correspond au code.
Champs obligatoires à la réceptionÀ la construction, l'identifiant et l'horodatage sont remplis automatiquement. Mais un message reçu sans identifiant est rejeté : en inventer un casserait la traçabilité.

Ce que le contrat refuse

En plus des types de champs, des règles de cohérence sont vérifiées à chaque validation :

  • un fait traité avant de s'être produit, ou un événement qui se cite lui-même comme cause ;
  • un sens, une action ou une zone hors des listes fermées, un champ inconnu ;
  • une version de schéma inconnue, un horodatage sans fuseau horaire ;
  • un agent à règles qui déclarerait un palier ou un appel LLM ; une décision LLM sans son coût ;
  • un message livré avant d'avoir été émis, un message direct sans destinataire ;
  • un déplacement qui ne change pas de zone, un stock sans zone.
